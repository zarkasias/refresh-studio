## 1. Goal and gate

**PRD (Milestones):** "M1 Audit MVP | Capture, platform detection, Lighthouse + axe, auditor, report | **Report sent to 3 real prospects**"

PRD sections this milestone builds: **1. Capture** (≤ 25 same-domain pages, robots.txt, DOM, screenshots at 390 and 1440, images, fonts, colors, platform plus theme/page builder, recorded consent), **2. Audit** (Lighthouse mobile and desktop, axe per page, small-business checks, five 0–100 scores, plain-English report with top 5 fixes, what can wait, annotated screenshots, "Consultant edits"), and the **Auditor** row of In-product agents ("Scored report, top 5 fixes | Consultant edits").

M1 is done when all of these hold:

1. **`pnpm gate:m1` passes.** At least **3 distinct prospect projects** (consent method not `own-site`) each have: consent recorded *before* their first capture started; a `ReportVersion` with `approvedAt` and `approvedBy`; and a `ReportDelivery` that points at that approved version. (CLAUDE rules 4 and 5.)
2. `pnpm typecheck && pnpm lint && pnpm test && pnpm eval:capture && pnpm eval:checks` exit 0 offline in CI. `eval:checks` has **zero unexpected fires on arc-electric** (the control site) and every "fires" expectation in section 5 is met.
3. `pnpm eval:auditor` has **zero hard failures** and a soft score ≥ 0.8, with the run appended to `evals/auditor/history.json`.
4. A real capture and audit of chambers-consulting.dev is committed as a fixture (T34), and one end-to-end dogfood report has been approved and exported (T35).
5. ADRs 007–010 (section 7) are committed with status `accepted`.
6. Every network request from capture and audit goes through `guardedFetch`/`guardedGoto`, which call `assertCrawlAllowed` and the robots check. A lint rule plus a test prove there is no other path (T8, T39).

**The gate needs consultant work that engineering can't do.** No prospect site may be crawled until its owner's consent is recorded (rule 5). Getting 3 consents is the critical path. Outreach (T36) starts on day 1, in parallel with the build. Plan for 5–6 requests to get 3 yeses.

## 2. Changes to the site model (these come first: T1–T3)

### 2a. Site document v3 (T1, ADR-007)

| Change | Why |
|---|---|
| `Site.schemaVersion: 3` | Required by any document shape change (ADR-003 consequence). |
| `brand.extractedFonts: ExtractedFont[]` where `ExtractedFont { family: string; raw?: string[] }`. `family` is the normalized name (`Avenir`, `DIN Next`, `system-ui`). `raw` lists the names as found in computed styles (`avenir-lt-w01_35-light1475496`), non-empty, unique, and omitted when it equals `family`. Families are unique per site. | Requirement 1 and M1-notes "Raw Wix font names". The raw name carries weight/style hints (`35-light`) and lets us debug a wrong normalization. The audit's font-count check and the M2 designer read `family`. |
| `KnownPageBuilderSchema` gains `'kadence-blocks'` and `'beaver-builder'` | Both appear in the manifest (jolly-plumbing, iphci) and currently pass through the open `Slug` branch. Making them known lets detection, exporter path selection and evals switch on them exhaustively. They were already valid slugs, so no data changes. |
| Migration step `v2ToV3` in `migrateSiteDoc`: `extractedFonts: string[]` → `[{ family }]`, de-duplicated by family | ADR-006 pattern. Read paths don't change. Approved Version snapshots are migrated on read, never rewritten (ADR-005). |

The 10 labels, the `_template` and `LABELING.md` move to v3 in the same PR, converted mechanically by the migration. Labels gain `raw` only where the labeler recorded it (none today).

**Alternative (D1):** keep `extractedFonts: string[]` (normalized) and put raw names only in capture records (2b). That needs no v3. It is rejected as the default because raw names then live outside the model the exporters read.

**Not changed:** sections, business, tokens, `platformEvidence.where`.

### 2b. Capture records (T2, new schemas in `packages/site-model/src/schemas/capture.ts`, migration 0003)

These are stored next to the Site, not inside it. The Site is what capture *concluded*; these records are what it *saw*, and the audit needs both.

```

  protocol: 'http' | 'https'; title: string; metaDescription?: string
```

Tables: `crawls` (CaptureRun columns, `planned`/`skipped`/`robots` as JSONB) and `captured_pages` (`facts`, `axe` as JSONB), both cascading from `projects`. `crawls.site_id` is nullable and `ON DELETE SET NULL`, so rebuilding a Site keeps the crawl evidence (consultant decision, 2026-11-09). Hidden copies and slider clones never appear in `PageFacts`; that is enforced at extraction (T10).

**T4 Fixture server and network lockdown.** `evals/fixtures/server.ts` serves a directory on `127.0.0.1:<random port>`. `lockdownContext(context)` installs a Playwright route that **aborts every request whose host is not loopback**, and logs it. Fixture platform URLs such as `static.wixstatic.com/...` are fulfilled from local files by URL pattern, never fetched. `fixtureProject(port)` returns a Project with `consent.method: 'own-site'` scoped to the loopback origin, so `assertCrawlAllowed` still runs in tests. *Acceptance:* a test page that requests a real external URL produces an aborted request and zero sockets to non-loopback addresses (checked with a `net.connect` spy in Node).

**T5 Label anonymizer (D8).** `anonymize(label, seed)` is deterministic: business names → `Acme <Type> Co`; phone numbers → `555-01xx` fictional numbers, mapped **consistently per distinct number** so a mismatch stays a mismatch; emails → `@example.com`; addresses → fictional street plus the real state/ZIP shape; people → fictional names; long body text → lorem-free neutral text of the same length. Kept unchanged: structure, section types, hours *times* and day ranges (they are patterns, not identity), hex colors, font families, CTA kinds and providers, and URL shapes (paths). Hidden characters and percent-encodings inside hrefs are preserved byte for byte. *Acceptance:* snapshot tests on jolly-plumbing (zero-width space survives; two numbers stay distinct), casper-plumbing (href digits ≠ display digits after mapping), and hair-and-co-brooklyn (`%28...%29%20` survives). A test asserts no original phone, email or business name appears in any output.

**T6a Synthetic site generator.** `buildSyntheticSite(anonLabel, recipe)` writes static HTML/CSS/JS pages to `evals/fixtures/sites/<slug>/`. Each section is rendered from the label. The **recipe** (`evals/fixtures/recipes/<slug>.ts`) adds the patterns: platform markers from manifest `evidence`, fonts as computed names, colors on real text, plain-text phones where the label says "(not linked)", hidden copies, and so on. Expected outputs are the anonymized label plus `expected.capture.json` (what extraction must find). First three recipes: **casper-plumbing** (Wix markers, Wix internal font names, href/display mismatch, plain-text phones), **iphci** (WordPress markers, `.slick-cloned` duplicates of the Plumbing/Heating/Cooling blocks, `data-cfemail` email, `href="#"` Services toggle with submenu), **delaware-valley-hardwoods** (custom, Instagram-style feed showing "Loading recent projects..." that a script replaces after 1.2 s). *Acceptance:* the three sites build reproducibly (same bytes for the same seed); `pnpm eval:capture` can serve them.

**T7 Audit labels (user, about 10 minutes per site).** `evals/sites/<slug>/expected.audit.json`: `{ checks: { [CheckId]: { expect: 'fires' | 'silent' | 'unknown'; note?: string } } }`, prefilled by agent-engineer from section 5. **T8a Fixture-only loopback URLs (prerequisite for T8; consultant decision, 2026-11-09).** The production `UrlSchema` stays strict (no loopback hosts), so a real project can never target localhost from the worker. `packages/site-model` adds a separate fixture-only URL schema that also accepts `http://127.0.0.1:<port>`, `localhost` and `[::1]`, and a way to validate capture records, Projects and Sites against it in tests and fixture runs only (for example a schema factory parameterized by the URL schema). Production code paths (`rowTo*` mappers, jobs, the app) always use the strict schema. `evals/fixtures` `fixtureProject` drops its tolerated-issue workaround and validates fully with the fixture schema. Recorded in ADR-010. *Acceptance:* the strict schemas still reject `http://127.0.0.1:3000/`; the fixture variants accept it; `fixtureProject` validates fully; a lint rule or test shows the fixture schema isn't imported outside `evals/` and test files.

**T8 Robots, discovery, guarded network path.**
- `robots.ts` uses **`robots-parser`**. Our token (`SiteRefreshStudio`, D11) and `*` are both honored. 4xx means allow all; 5xx or a network error means disallow all and the run is `blocked`. `Crawl-delay` is honored up to 10 s.
- `discover.ts`: `/sitemap.xml` (plus `Sitemap:` lines in robots, sitemap indexes one level deep) plus homepage `<a>` links, normalized (strip hash, sort query, collapse trailing slash). Order: home, then pages whose path or link text matches contact/book/appointment/about/services/menu/locations, then nav order, then sitemap order. The list is cut at `min(25, consent.scope.maxPages)`.
- `net.ts`: `guardedFetch` and `guardedGoto` are the only functions allowed to touch the network. Each calls `assertCrawlAllowed` with a fresh project read and `pagesCrawledSoFar`, checks robots, and re-checks the **final URL after redirects**.
- An ESLint `no-restricted-syntax` rule bans `fetch(`, `page.goto(`, `request.get(` and `http.get` elsewhere in `packages/{capture,audit}`.
*Acceptance:* tests for: a robots-disallowed path (skipped with reason `robots`); robots 503 (run blocked with a plain message); a 26th URL (skipped `page-limit`); a redirect to another origin (refused); a wixsite `pathPrefix` (outside paths skipped); and the lint rule catching a planted `fetch(` in a fixture file.

**T9 Page capture.**
- Playwright Chromium, 30 s navigation timeout.
- Waits: `networkidle` with a 15 s cap, then a 1.5 s settle. A lazy-load scroll to the bottom in viewport steps, then back to the top. A placeholder poll (visible text matching `/^loading\b/i`, `[aria-busy="true"]`) until it clears or the 15 s cap is reached. Anything still pending goes to `pendingContent`, and its placeholder text is excluded from facts.
- Screenshots: full page at 390×844 and 1440×900.
- HTML: `page.content()` after the waits.
- Trackers are blocked by a small host list. Fonts, images and same-page third-party embeds still load.
- iframes: `src` is recorded, never navigated into (rule 6).
- **Bot challenge** (`cf-mitigated: challenge` header or the challenge page title): stop the page with `bot-challenge` and never try to get past it.
- Assets are uploaded through an injected `Storage` interface (side effect at the edge).
- **Asset owner (consultant decision, 2026-11-09):** `Asset.siteId` is required, so the crawl job creates a stub Site (business name from the project, `pages: []`) before uploading the first screenshot or HTML asset; T13 fills it in. No schema change.

**T17 Hours and NAP checks.** `hours/parse.ts` is a small deterministic parser. ## 4. Consent, fixtures and network policy

- **Who may be crawled:** chambers-consulting.dev (own-site) and prospects with consent recorded in T29. No manifest site with `consent: none` is crawled, fetched, HEAD-checked or run through Lighthouse. That includes the `https` check: we never probe `http://` on a site we don't have consent for.
- **Two consent records, two purposes.** `project.consent` (DB) allows the audit. A manifest entry becomes `granted` only if the owner also agreed to the test-site use (D17). `selectNetworkEligible()` stays the only gate for evals and fixture recording.
- **Offline tests and evals.** Every capture test runs against `evals/fixtures` on loopback with external requests aborted (T4). CI never touches the internet.
- **Fixture sources:**
  1. Anonymized label-derived synthetic sites (T5–T6). Structure and patterns come from the labels; names, numbers, emails, addresses and people are fictional.
  2. Pattern fixtures with no label behind them.
  3. Real captures of network-eligible sites only (T34, later consenting prospects).
- **Limitation, stated plainly:** synthetic sites are generated by us, so they test our handling of patterns we already know about, not unknown real-world mess. Real-world accuracy is measured only on chambers-consulting and on prospects who agree to the test-site use.
- **Prospect data:** private buckets, signed URLs, deleted after 90 days for prospects who don't engage (D18), deleted on request at any time.

## 6. Report flow and format

1. **Draft.** The audit job writes ReportVersion 1. The template (T22) always runs; the auditor agent (T23) refines it when a key is set.
2. **Edit.** The consultant edits wording, moves findings, dismisses false positives with a reason, and toggles crops. Scores can't be typed in. They change only by deterministic recomputation after a dismissal, and the dismissal is recorded on the version.
3. **Approve.** `assertReportApprovable` → `approvedAt`/`approvedBy`. The version is frozen (trigger). Later edits create version n+1.
4. **Share/export.**
   - PDF of a specific approved version (stamped with its number and approval date).
   - Private link that always shows the newest approved version.
   - Both require `approvedAt` (rule 4).
5. **Send.** The consultant emails it from his own mail (no email service in M1) and clicks "Mark as sent", which creates a `ReportDelivery`. That is what `gate:m1` counts.

**Format (D3):** the **PDF by email is the gate path**, because it needs no hosting. The share link is built in M1 but switched on only once hosting is decided (D10). If hosting slips, the PDF alone meets the gate.

## 7. ADR drafts (to commit as `accepted` after review)

- **007 — Site model v3: fonts and page builders.** Context: M1-notes Wix fonts; manifest builders on the slug branch. Decision: section 2a. Consequences: labels move to v3; one migration step; exporters read `family`; designer (M2) can use `raw` hints.
- **008 — Audit records and report approval.** Context: rule 2 (tool scores), rule 4 (approval), PRD "Consultant edits". Decision: section 2c. ReportVersion follows ADR-005 (frozen, newest only, numbered). Scores are copied from the AuditRun and checked by recomputation before approval. Dismissals are recorded and recompute deterministically. Share tokens are stored hashed. Generic versioning core shared with variants. Consequences: one more freeze trigger; the "Looks current" score is deterministic in M1.
- **009 — Jobs and runtime.** Context: Chromium and Lighthouse don't fit in a Next.js serverless bundle; rule 5/6 enforcement must be unavoidable. Decision: Inngest functions served by `apps/worker`; local-first (Inngest dev server on the consultant's machine) for M1; one guarded network path (`guardedFetch`/`guardedGoto`) enforced by lint; consent re-checked every page step; bot challenges stop the page and are never bypassed. Consequences: a hosted worker is a later decision (D10); the UA token is published.
- **010 — Fixtures without crawling (amends ADR-004).** Context: the consultant asked for synthetic HTML built from the labels; ADR-004 says "copy a pattern, never content". Decision: label-derived synthetic sites are allowed **only after anonymization** (T5); pattern fixtures need no label; fixture-only loopback URL schema, with production schemas staying strict (T8a); all tests run with external requests aborted; real captures only through `selectNetworkEligible`. Consequences: evals measure pattern handling, not real-world accuracy, until consenting prospects add real fixtures.

## 9. Risks

- **Gate depends on 3 consents** (T36). This is on the calendar, outside engineering control. Start now; ask more prospects than you need.
- **Synthetic overfitting:** checks pass on fixtures we built. Mitigation: T7 audit labels from real browsing, the T34 real capture, and the consultant reviewing every prospect report before it goes out.
- **False positives in front of prospects** damage trust in the service. Mitigation: the arc-electric control rule; parsers that only fire on clear evidence (hours, phones); dismissal with recompute; never more than 5 fix-now items.
- **Lighthouse runtime and variance:** 25 pages × 2 presets may take 20–30 minutes; single runs vary by a few points. Scores are reproducible from the stored LHR, not from re-running.
- **Bot protection** (Cloudflare challenges) may block scans. We stop and say so; we never work around it.
- **Prompt injection** through page text into the auditor. Mitigation: the prompt treats inputs as data; the output can only reference known ids and numbers.
- **Prospect data in storage:** private buckets, a retention limit, delete on request.
- **Worker on a laptop:** fine for 3 prospects; not for client-facing reliability (D10).
- **Kit drift:** agent and skill files currently contradict ADR-004 and rule 2 until T38 lands.
